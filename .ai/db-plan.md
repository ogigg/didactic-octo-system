# Database Schema - AI Trainer MVP

## Overview

This schema supports the complete user journey from onboarding through personalized workout generation to detailed set-by-set logging and feedback. The design separates authentication (managed by Supabase Auth) from user profiles, distinguishes between planned workouts and actual execution, and supports offline synchronization.

## Tables

### 1. profiles

Stores user profile data linked 1:1 with Supabase Auth users.

```sql
CREATE TABLE profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,

  -- Onboarding data
  gender gender_type,
  goal goal_type NOT NULL,
  custom_goal TEXT,
  weekly_frequency frequency_type NOT NULL,
  onboarding_completed BOOLEAN NOT NULL DEFAULT FALSE,

  -- Timestamps
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT custom_goal_length CHECK (char_length(custom_goal) <= 500),
  CONSTRAINT custom_goal_required CHECK (
    (goal != 'custom') OR (goal = 'custom' AND custom_goal IS NOT NULL)
  )
);

COMMENT ON TABLE profiles IS 'User profiles with onboarding data, linked 1:1 with auth.users';
COMMENT ON COLUMN profiles.custom_goal IS 'Free-text goal when goal_type is custom. Subject to profanity filter on application layer.';
```

### 2. exercises

Local exercise library, seeded from external APIs and used for validation.

```sql
CREATE TABLE exercises (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- Exercise identification
  name TEXT NOT NULL,
  external_id TEXT UNIQUE, -- ID from source API (ExerciseDB, WGER)

  -- Exercise metadata
  primary_muscles TEXT[] NOT NULL, -- Array of muscle groups
  secondary_muscles TEXT[],
  equipment TEXT[] NOT NULL, -- Required equipment (stored as text array)
  difficulty_level TEXT, -- beginner, intermediate, advanced
  instructions TEXT, -- Brief execution instructions

  -- Media (optional for MVP)
  image_url TEXT,
  video_url TEXT,

  -- Timestamps
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT exercises_name_not_empty CHECK (char_length(name) > 0),
  CONSTRAINT exercises_primary_muscles_not_empty CHECK (array_length(primary_muscles, 1) > 0)
);

COMMENT ON TABLE exercises IS 'Local exercise library for validation and workout generation';
COMMENT ON COLUMN exercises.equipment IS 'Array of equipment names (e.g., ["barbell", "bench"])';
```

### 3. workout_sessions

Main entity representing a workout session (both plan and execution tracking).

```sql
CREATE TABLE workout_sessions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,

  -- Session metadata
  name TEXT, -- Workout title/name shown in UI
  status workout_status NOT NULL DEFAULT 'active',
  generation_source generation_source NOT NULL DEFAULT 'llm',

  -- Generation context (for future adaptation)
  goal_snapshot goal_type NOT NULL, -- Goal at time of generation
  custom_goal_snapshot TEXT,

  -- Session timing
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,

  -- Timestamps
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT workout_sessions_completed_after_start CHECK (
    completed_at IS NULL OR started_at IS NULL OR completed_at >= started_at
  )
);

COMMENT ON TABLE workout_sessions IS 'Workout session container tracking both plan and execution';
COMMENT ON COLUMN workout_sessions.generation_source IS 'Tracks whether session was generated by LLM or fallback mechanism';
COMMENT ON COLUMN workout_sessions.goal_snapshot IS 'Captures user goal at generation time for future analysis';
```

### 4. session_exercises

Junction table linking exercises to workout sessions, defining order and capturing per-exercise feedback.

```sql
CREATE TABLE session_exercises (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  workout_session_id UUID NOT NULL REFERENCES workout_sessions(id) ON DELETE CASCADE,
  exercise_id UUID NOT NULL REFERENCES exercises(id) ON DELETE RESTRICT,

  -- Exercise ordering within session
  order_index INTEGER NOT NULL,
  rest_duration_seconds INTEGER NOT NULL DEFAULT 60, -- Rest timer per exercise

  -- Optional AI-generated notes for this exercise in this session
  notes TEXT,

  -- Per-exercise difficulty feedback (collected post-execution)
  difficulty_feedback difficulty_feedback,

  -- Timestamps
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT session_exercises_unique_exercise_per_session
    UNIQUE (workout_session_id, exercise_id),
  CONSTRAINT session_exercises_unique_order_per_session
    UNIQUE (workout_session_id, order_index),
  CONSTRAINT session_exercises_order_positive CHECK (order_index >= 0),
  CONSTRAINT session_exercises_rest_positive CHECK (rest_duration_seconds >= 0)
);

COMMENT ON TABLE session_exercises IS 'Defines which exercises are included in a workout session and their order';
COMMENT ON COLUMN session_exercises.order_index IS 'Zero-based index defining exercise order within session';
COMMENT ON COLUMN session_exercises.difficulty_feedback IS 'User feedback on exercise difficulty (collected after completion)';
```

### 5. session_sets

Defines the planned/suggested sets for each exercise in a session.

```sql
CREATE TABLE session_sets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  session_exercise_id UUID NOT NULL REFERENCES session_exercises(id) ON DELETE CASCADE,

  -- Set identification
  set_number INTEGER NOT NULL, -- 1-based set number
  set_type TEXT NOT NULL DEFAULT 'working', -- 'warmup' or 'working'

  -- Suggested/target values (AI-generated or rule-based)
  target_load_kg DECIMAL(5, 2) NOT NULL, -- kg with 2 decimal places
  target_reps INTEGER NOT NULL,

  -- Timestamps
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT session_sets_unique_set_per_exercise
    UNIQUE (session_exercise_id, set_number),
  CONSTRAINT session_sets_set_number_positive CHECK (set_number > 0),
  CONSTRAINT session_sets_set_type_valid CHECK (set_type IN ('warmup', 'working')),
  CONSTRAINT session_sets_target_load_non_negative CHECK (target_load_kg >= 0),
  CONSTRAINT session_sets_target_reps_positive CHECK (target_reps > 0)
);

COMMENT ON TABLE session_sets IS 'Planned/suggested sets for each exercise with target load, reps, and rest time';
COMMENT ON COLUMN session_sets.target_load_kg IS 'Suggested weight in kilograms (MVP uses kg only)';
```

### 6. set_logs

Records actual execution of each set by the user. Highest-growth table.

```sql
CREATE TABLE set_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  session_set_id UUID NOT NULL REFERENCES session_sets(id) ON DELETE CASCADE,

  -- Actual performance
  actual_load_kg DECIMAL(5, 2),
  actual_reps INTEGER,
  rpe DECIMAL(3, 1), -- Rate of Perceived Exertion (1-10)

  -- Completion status
  completed BOOLEAN NOT NULL DEFAULT FALSE,
  not_completed_reason TEXT, -- Optional reason when completed = FALSE

  -- Timing
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,

  -- Timestamps (for offline sync)
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Constraints
  CONSTRAINT set_logs_actual_load_non_negative CHECK (
    actual_load_kg IS NULL OR actual_load_kg >= 0
  ),
  CONSTRAINT set_logs_rpe_range CHECK (
    rpe IS NULL OR (rpe >= 1 AND rpe <= 10)
  ),
  CONSTRAINT set_logs_actual_reps_positive CHECK (
    actual_reps IS NULL OR actual_reps > 0
  ),
  CONSTRAINT set_logs_completed_requires_values CHECK (
    (completed = FALSE) OR (actual_load_kg IS NOT NULL AND actual_reps IS NOT NULL)
  ),
  CONSTRAINT set_logs_completed_after_start CHECK (
    completed_at IS NULL OR started_at IS NULL OR completed_at >= started_at
  )
);

COMMENT ON TABLE set_logs IS 'Actual execution logs for each set. Highest-growth table, candidate for future partitioning.';
COMMENT ON COLUMN set_logs.not_completed_reason IS 'Optional user-provided reason for not completing the set';
```

### RPC Function: get_workout_session_detail

Returns a full workout session with nested exercises, sets, and logs as JSONB. Uses `SECURITY DEFINER` with manual `auth.uid()` ownership check. Called from the mobile app to load complete workout history in a single round-trip.

**Parameters:** `p_session_id UUID`
**Returns:** JSONB with structure: `{ id, name, status, exercises: [{ exercise_name, sets: [{ set_type, target_load_kg, log: { actual_load_kg, rpe, completed } }] }] }`

BEGIN
  NEW.updated_at = NOW();

## Relationships

### Entity Relationship Summary

```
auth.users (Supabase)
  ↓ 1:1
profiles
  ↓ 1:N
workout_sessions
  ↓ 1:N
session_exercises ←→ N:1 exercises
  ↓ 1:N
session_sets
  ↓ 1:N
set_logs
```

### Detailed Relationships

1. **auth.users → profiles** (1:1)
   - One Supabase auth user has exactly one profile
   - CASCADE delete: when auth user is deleted, profile is deleted

2. **profiles → workout_sessions** (1:N)
   - One user can have many workout sessions
   - CASCADE delete: when profile is deleted, all sessions are deleted

3. **workout_sessions → session_exercises** (1:N)
   - One workout session contains many exercises
   - CASCADE delete: when session is deleted, all session exercises are deleted

4. **exercises → session_exercises** (1:N)
   - One exercise can be used in many workout sessions
   - RESTRICT delete: cannot delete an exercise that's been used in any session

5. **session_exercises → session_sets** (1:N)
   - One session exercise has many sets
   - CASCADE delete: when session exercise is deleted, all its sets are deleted

6. **session_sets → set_logs** (1:N)
   - One planned set can have multiple log entries (though typically just one)
   - CASCADE delete: when set is deleted, all its logs are deleted

## Data Integrity Considerations

### Validation at Database Level

1. **CHECK Constraints**: All numeric fields (reps, load, rest time) have positive value checks
2. **NOT NULL Constraints**: Critical fields are marked NOT NULL to prevent incomplete data
3. **UNIQUE Constraints**: Prevent duplicate exercises in sessions, duplicate set numbers
4. **Foreign Key Constraints**: Maintain referential integrity across all relationships
5. **ENUM Types**: Limit possible values for status fields and feedback

### Application-Level Validation

The following validations should be enforced at the application layer:

- Profanity filtering for `custom_goal` and `not_completed_reason`
- Maximum character limits beyond CHECK constraints
- Complex business rules (e.g., minimum rest time based on intensity)
- Cross-field validations

## Offline Synchronization Strategy

### Client-Side UUID Generation

All tables use UUID primary keys that can be generated client-side using `gen_random_uuid()` or equivalent client libraries. This enables:

- Offline workout logging without server round-trips
- Idempotent inserts (same UUID = same record)
- Conflict-free merging on sync

### Timestamp-Based Conflict Resolution

All tables include `created_at` and `updated_at` timestamps:

- `created_at`: Immutable record creation time
- `updated_at`: Last modification time (updated via trigger)

Conflict resolution strategy: **Last Write Wins (LWW)** based on `updated_at` timestamp.

### Sync Implementation Notes

1. Client maintains a local SQLite database mirroring the server schema
2. On connectivity loss, all mutations are queued locally
3. On connectivity restoration:
   - Queue is processed with exponential backoff
   - Server rejects records with older `updated_at` if newer version exists
   - Client merges server response and resolves conflicts locally

## Performance Considerations

### Query Optimization

1. **Composite Indexes**: Created for common query patterns (user_id + status, user_id + created_at)
2. **GIN Indexes**: Used for array columns (primary_muscles, equipment) to enable efficient containment queries
3. **Covering Indexes**: Future optimization opportunity for frequently accessed column combinations

### Scalability Paths

1. **Partitioning**: `set_logs` table is a candidate for range partitioning by `created_at` as it grows
2. **Archiving**: Old completed sessions (>6 months) can be moved to archive tables
3. **Materialized Views**: Summary statistics (total tonnage, PRs) can be pre-computed for dashboards

### Current MVP Limitations

- No pagination strategy defined (acceptable for MVP user base)
- No read replicas or caching layer
- All queries hit primary database

---

## Security Considerations

### Row-Level Security (RLS)

- **Mandatory**: RLS is enabled on all user-data tables
- **Principle**: Users can only access their own data via `auth.uid()` check
- **Exercises**: Public read for authenticated users, write restricted to service role

### Data Sensitivity

- **PII**: Minimal personal data stored (gender optional, no name/address)
- **Audit Trail**: `created_at` and `updated_at` provide basic audit capability
- **Soft Delete**: Status-based deletion preserves data for analytics while preventing user access

### Authentication Integration

- All policies rely on Supabase Auth's `auth.uid()` function
- No application-level user_id passing required
- JWT tokens handled by Supabase client libraries

## Future Enhancements (Post-MVP)

### Schema Evolution Paths

1. **Equipment Inventory**: Separate `user_equipment` table to track available equipment per user
2. **Exercise Substitutions**: `exercise_alternatives` table for AI to choose fallbacks
3. **Training Programs**: `programs` table for multi-week periodized plans
4. **Exercise Media**: Expand `exercises` with detailed form cues, common mistakes
5. **Social Features**: `workout_shares`, `follows`, `comments` tables
6. **Gamification**: `achievements`, `badges`, `streaks` tables
7. **Body Metrics**: `body_measurements` table for weight, body composition tracking
8. **Raw LLM Logs**: `llm_responses` table for debugging and fine-tuning

### Denormalization Opportunities

- Pre-computed workout summaries (tonnage, duration, volume)
- User PR (personal record) cache table
- Last N workouts materialized view for quick AI context

## Migration Strategy

### Initial Migration Order

```sql
1. Create custom ENUM types
2. Create profiles table (depends on auth.users)
3. Create exercises table (independent)
4. Create workout_sessions table (depends on profiles)
5. Create session_exercises table (depends on workout_sessions, exercises)
6. Create session_sets table (depends on session_exercises)
7. Create set_logs table (depends on session_sets)
8. Create indexes
9. Enable RLS on all tables
10. Create RLS policies
11. Create triggers (updated_at automation)
```

### Seeding Requirements

1. **exercises**: Must be seeded from ExerciseDB/WGER API before first user onboarding
2. **Minimum viable exercise library**: ~100 exercises covering major movement patterns
3. **Equipment list**: Standardized equipment names for validation

   - Index usage statistics
3. **RLS Policy Performance**:
   - Policy check execution time
   - Policy cache hit rate

4. **Generation Source Distribution**:
   - Percentage of workouts from LLM vs fallback
   - Tracks AI system reliability

### Alerting Thresholds

- `set_logs` table size exceeding 1M rows (consider partitioning)
- More than 10% of workouts using fallback generation
- RLS policy execution time >50ms (p95)

## Backup and Recovery

### Supabase Managed Backups

- Daily automated backups (Supabase default)
- Point-in-time recovery (PITR) available
- Backup retention: 7 days (MVP), increase for production

### Critical Data Priority

1. **Tier 1 (Critical)**: `profiles`, `workout_sessions`, `set_logs`
2. **Tier 2 (Important)**: `session_exercises`, `session_sets`
3. **Tier 3 (Recoverable)**: `exercises` (can be re-seeded from external API)

## Compliance and Privacy

### Data Retention

- **Active Users**: All data retained indefinitely
- **Deleted Accounts**: CASCADE delete removes all user data within 30 days
- **Inactive Users**: No automatic deletion (out of MVP scope)

### GDPR Considerations

- Right to access: Query all tables filtered by user_id
- Right to deletion: CASCADE delete from profiles triggers full removal
- Right to portability: Export JSON from all user-owned tables
- Data minimization: Only essential data collected during onboarding

### Data Residency

- Supabase region configuration determines data storage location
- Recommend EU region for GDPR compliance if targeting European users

## Conclusion

This schema provides a solid foundation for the AI Trainer MVP. It balances normalization with query performance, supports offline-first architecture, and incorporates comprehensive security through RLS policies. The design anticipates future growth with strategic indexes and clear evolution paths while maintaining simplicity for MVP requirements.

Key strengths:

- **Separation of concerns**: Plan vs execution, auth vs profile
- **Data integrity**: Comprehensive constraints and foreign keys
- **Security**: Mandatory RLS with principle of least privilege
- **Offline support**: UUID generation and timestamp-based conflict resolution
- **Observability**: Generation source tracking for AI system monitoring

The schema is ready for migration implementation and can scale to thousands of users before requiring architectural changes.
